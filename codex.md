# Cloudflare Wiki / Emby Wiki — project context

## Origin and initialization boundary

Repository: `jacklilyhello/cloudflare-wiki`. This is an independent greenfield implementation. The owner abandoned `jacklilyhello/Cloudflare-Native-Wiki` as an unfinished project. Its code, data, migrations, Astro architecture and infrastructure choices must not be inherited. This records the owner's decision, not an assessment of unseen legacy code.

The product combines **emby.wiki's documentation organization**, **Wiki.js 3's visual and interaction direction**, and **Cloudflare Native architecture**. Wiki.js is a product reference, not a source-code port: do not copy its Node.js server, PostgreSQL or GraphQL backend. Ground later UI development in then-current product references; initialization does not attempt the full UI.

Initialization is complete. A separate product-development task authorizes the Git/PR/CI/squash/test-deployment loop and goal mode. The current implementation includes a public reader, shared Markdown renderer, D1 publication/revision services, indexed bilingual search, single-administrator authentication, visual navigation and redirect management, an administrator audit trail and a content workspace with Monaco editing, preview, publication controls and version history/diff. Assets and site settings remain subsequent work; do not report them as implemented.

## Product contract

### Two identities and one administrator

Anonymous visitors never register or log in. They read published documentation, search, switch language, copy code, view images and download public attachments. Drafts/private files/admin revisions must not leak through public endpoints or caches.

There is exactly one owner-configured administrator. Implemented capabilities are one-time setup, login/logout, dashboard reads, username/password changes requiring the current password, page creation/editing, draft saves, publication/unpublication, move/rename, soft deletion, restoration, revision history/diffs, visual navigation and redirect management, and audit reads. Assets/files and site settings remain future UI capabilities. Every privileged request must verify the sole administrator, including content, navigation, redirect and audit APIs and future assets. A hidden SPA route is not authorization. Cloudflare Access is not provisioned.

`/admin` lazy-loads the bilingual React admin UI and CSS; `/admin/account` provides account changes, `/admin/pages` the content list, `/admin/navigation` independent language trees and `/admin/audit` the audit trail. The Worker shell contains no draft/account data, and each admin API verifies its own access. Exact editor/history document routes additionally require a session before receiving their shell. `GET /api/admin/setup` exposes only two booleans, `initialized` and `setupAvailable`. Setup/login require an exact same-origin request; authenticated changes also verify a session-bound CSRF token. `worker/admin-http.ts` streams JSON with a 4 KiB default for authentication; content routes select a 1 MiB maximum and navigation a 500 KiB maximum. Cookie ambiguity is rejected, errors omit storage/credential details, and dynamic admin responses are no-store and noindex.

`migrations/0004_administrator.sql` enforces a singleton administrator and bootstrap, stores hashed session bearers, and records login limits. Passwords use a random 16-byte salt and fixed scrypt profile (`N=16384`, `r=8`, `p=5`, 32-byte output, 32 MiB maximum memory); no stored value may choose a work factor. At most two password derivations run concurrently per isolate. Login/setup each allow five attempts per IP and 30 globally per ten-minute window before password hashing; credential changes apply equivalent limits per session and globally. Global exhaustion prevents new IP rows, and indexed expiry cleanup is bounded.

Sessions use 32 cryptographically random bytes in a host-only `__Host-wiki_session` cookie with Secure, HttpOnly and SameSite=Strict; only a SHA-256 hash reaches D1. Absolute lifetime is eight hours, idle lifetime 30 minutes, and activity touches are monotonic and throttled to once a minute. Logout revokes the current session. Username/password updates compare the current credential version and a still-valid session in SQL, then atomically increment the version and revoke every session through a trigger. Setup checks the unconsumed, unexpired bootstrap token and administrator absence inside the creation transaction; losing requests cannot create another account or session. There is no recovery/reset interface or automatic reinitialization.

Setup confirms the administrator insert and bootstrap consumption using their `RETURNING id` rows, not D1 `meta.changes`, which includes trigger side effects. Deploy this compatible setup implementation before applying `0007_audit.sql`, because Actions applies migrations before updating the Worker. Any application rollback that retains the audit triggers must retain this setup behavior too.

Excluded: ordinary accounts/login, registration, groups, RBAC, comments, watches, notifications, suggested edits, approval workflows, live collaboration and multisite.

### Chinese and English only

The closed language union is `zh | en` in `shared/contracts.ts`. Articles have stable identities with Chinese and English versions and language-specific slugs. Translation relationships must survive moves/renames. Navigation is separate per language; search ranks the current language first. Missing translations must be explicit. Do not build a general dozens-of-locales platform. The final header offers `中文 | English`.

### Markdown only

The administrator editor uses Monaco with live preview, loaded only on `/admin/pages/new` or `/admin/pages/{id}/edit`; the history route loads its diff editor as needed. It edits Markdown plus title, description, tags and change notes, offers write/split/preview modes, and links the other language through the stable page identity. Save and publish are explicit actions. Unsaved editor input stays in memory, with a navigation warning, download and session-reconnect path. A stale write does not silently overwrite or merge another tab's changes. No visual, AsciiDoc or blog editor is provided.

`shared/markdown.ts` implements a portable unified/remark/rehype AST pipeline for the reader and authenticated `POST /api/admin/preview`, which returns `{html,toc}` without persistence. GFM, footnotes, internal wiki links, callouts, directive groups, highlighting and KaTeX MathML are transformed before final explicit sanitization. The 128,000-byte Markdown source limit and node/nesting/code/diagram/math limits also apply to preview and draft validation. Per-render provenance prevents raw HTML from forging enhancement properties. The browser lazily renders Mermaid with strict settings, displays sanitized SVG as an image and retains the source. Sanitize after transformations with explicit element/attribute/protocol allowlists. Disallow scripts, event handlers, author styles and unsafe URLs. Store Markdown source and immutable revision metadata. A single editor does not make stored HTML trusted.

`shared/admin-routes.ts` is the exact route parser used by both UI and document policy. Entering editor/history uses full document navigation. `worker/editor-policy.ts` creates 18 random bytes per response and binds their nonce to the CSP header and inert meta element. Monaco's dynamic style elements require that nonce; only authenticated editor/history documents add `style-src-attr 'unsafe-inline'` for layout. Script policy remains `script-src 'self'`, workers use `worker-src 'self'`, and no `unsafe-eval`, CDN or blob-worker allowance is introduced. Reader, login, dashboard, account and page-list policies remain strict. Markdown sanitization continues to remove author styles before HTML enters this document.

Monaco is pinned in the lockfile. `scripts/monaco-csp.ts` fingerprints the two upstream style constructors and Monaco's embedded DOMPurify module, then applies narrow Vite transforms. A matched source hash/constructor change stops the build for review. The sanitizer replacement creates a separate instance of the pinned top-level DOMPurify; an npm override alone would not replace Monaco's vendored copy. Keep its hooks/configuration isolated from Mermaid. `optimizeDeps.exclude` preserves these reviewed transformations during local development; do not replace them with global DOM interception or a broader script policy.

### Public experience

The reader provides a header, nested left navigation, main article and right TOC; responsive navigation, dark mode, breadcrumbs, current-page highlighting, search, language switching, last updated, code copy and friendly 404. The Worker renders article HTML plus canonical, alternate-language and OpenGraph metadata and a fixed-origin sitemap. Original starter articles are initialized once by `migrations/0003_starter_content.sql`; `content/` preserves their reference Markdown. Public reads in `worker/content/public.ts` join the current publication pointer to its owned immutable D1 revision. Drafts, deleted pages and unpublished translations cannot enter public article, navigation, translation, search or sitemap results. Content mutations are confined to authenticated admin routes. Test is deliberately noindex and blocked in robots.txt.

## Architecture decision

Selected: **React 19 + TypeScript + Vite 8 + official Cloudflare Vite plugin + one module Worker with Workers Static Assets**. Versions are pinned in the lockfile. Node 24 is local/CI tooling, never a persistent production server.

React supports the server-rendered reader and lazy admin UI, with Monaco for editing and source diffs. Vite gives a familiar, small build surface and fast local updates. Cloudflare's official plugin runs backend code in workerd locally and builds the Worker and assets together. A Web-standard Worker keeps the initial backend small; evaluate Hono only when routing complexity warrants it. SSR meta-frameworks were considered, but impose extra conventions before article requirements exist. This choice does not inherit Astro.

`worker/reader.tsx` renders the same React reader used by browser hydration into the Vite HTML shell using HTMLRewriter. Inert JSON hydration data escapes HTML delimiters, and dynamic responses receive explicit security headers. Article content and metadata do not rely on client JavaScript. The admin UI is client-only; `worker/admin.ts` and `worker/auth/` own HTTP and authentication. Dynamic responses remain no-store so publication and unpublication take effect through authoritative D1 reads without stale public caches.

| Path | Responsibility |
| --- | --- |
| `src/` | SSR-compatible React reader and browser enhancements; no server secrets |
| `worker/` | HTTP, publication reads and transactional content/revision services |
| `shared/` | Portable reader/content contracts, safe Markdown and full-text query normalization |
| `public/` | Assets, static headers, test robots policy |
| `tests/` | Workerd D1 transaction/HTTP tests and deployment-policy tests |
| `migrations/` | Ordered immutable D1 schema and initial content migrations |
| `scripts/` | Guarded deployment and local/remote smoke checks |
| `.github/workflows/` | CI and deployment |
| `.github/rulesets/` | Reviewable main protection policy |

Every request runs the Worker first. `/assets/*`, favicon and robots use Cloudflare asset serving; documents, health, search, sitemap and administration use explicit Worker handlers. Unknown public API routes return JSON 404 and unknown documents return HTML 404, never successful SPA HTML. The `/api/admin` namespace requires authentication before dispatch except for its explicit setup/login endpoints. Health is uncached **liveness**, not a promise of database readiness. It exposes only service metadata and build revision.

Implemented domain: `worker/content/service.ts` creates translations, saves drafts, publishes the explicit current draft, unpublishes, moves paths, soft-deletes, restores deleted pages unpublished, and restores historical snapshots as new drafts. Stable page IDs link the two languages. Every change to an existing translation takes an expected write version; all side effects and the final version increment share a guarded D1 batch. Losing writers leave no orphan revision, event, route or search change. Revisions and audit events are database-immutable. Composite foreign keys keep draft/publication/restoration pointers inside their translation. Old paths resolve directly to the current path only while its page is published.

`worker/admin-content.ts` exposes these operations under `/api/admin/pages`, plus bounded revision/event reads and preview. It rejects unexpected JSON fields, repeated/unknown query keys, unsafe identifiers and methods. Read/write requests require a session; mutations and preview also require Origin/CSRF checks. `ContentService` requires an explicit `ContentWriteAccess` constructed server-side from that verified session's hash and credential version. `worker/auth/access.ts` supplies a live-session SQL predicate for all private reads and every write statement, including the first page/translation inserts. All statements in one content batch use the same time snapshot; logout or credential changes cannot bypass the SQL guard after asynchronous validation. A lost precondition yields 412, path/language collisions 409, invalid sessions 401 and storage failures a generic 503.

Page lists return draft metadata with language, literal title/path text and active/draft/published/deleted filters; they use stable timestamp/ID keyset cursors with at most 50 items. Detail includes the current draft, published snapshot and linked translations. History pages provide revision pagination, preview/source, a two-revision Monaco Markdown diff plus metadata differences, and an immutable event timeline. Restoring a historical revision is a new draft with a new revision ID; publication and current path remain unchanged. `0005_content_admin.sql` adds only listing indexes, preserving content and migration history.

D1 FTS5 indexes title, tags, description, path and readable body text only for published snapshots. Search projection, FTS row and publication pointer update atomically. NFKC normalization plus spaced Han tokens supports exact adjacent Chinese phrases; English words use Unicode tokenization. The query compiler quotes every token and combines terms with AND, never raw user FTS expressions. Queries are bounded to 200 characters and 30 results, language-filtered and weighted. Display text remains original. No replica routing or eventually consistent cache is used.

`worker/navigation/service.ts` stores a versioned tree per language and its stable nodes. `NavigationService` requires the same verified `ContentWriteAccess` as content; private reads and every statement of whole-tree replacement carry a live-session predicate. Expected-version checks guard deletion, bulk insertion and the final version increment together. Input validation bounds the forest to 300 nodes/eight levels, checks parent reachability/cycles and group-only nesting, rejects duplicate internal targets and sibling positions, and normalizes sibling order. Composite foreign keys keep parents and internal page targets within their language. Nodes link stable translation IDs, not mutable article paths.

Automatic mode derives navigation from currently published paths. Saving automatic mode retains the submitted custom nodes, but public reads ignore them; custom mode never falls back to automatic navigation, including for an empty tree. Public navigation joins current owned publication snapshots, suppresses unpublished/deleted targets and empty groups, and defaults internal labels to published titles. HTTP/HTTPS external links are validated without remote fetching and are excluded from active-page, breadcrumb and adjacent-article calculations. Removing an entry changes navigation only, not publication or search visibility. The authenticated `GET/PUT /api/admin/navigation/{language}` boundary accepts only its exact schema and closed language set, verifies Origin/CSRF on writes and returns generic storage failures. The visual editor is the administrator interface; users do not author JSON.

`worker/redirects/service.ts` manages noncanonical `page_routes` in a versioned language registry. Manual aliases and those created by page moves may be renamed, retargeted or deleted; canonical paths remain protected at both service and database boundaries, including unpublished/deleted pages. Targets are stable translation IDs in the same language and may be drafts, but deleted targets cannot be newly selected. Public resolution remains publication-only and follows the target's current canonical path directly, with no external destinations or redirect chains. Origin records creation provenance and is preserved when an automatic alias is edited.

`GET/POST/PUT/DELETE /api/admin/redirects/{language}` authenticates before dispatch; writes require exact Origin/CSRF and closed JSON of at most 4 KiB. POST takes `expectedVersion/path/translationId`, PUT additionally takes `sourcePath`, and DELETE takes `expectedVersion/sourcePath`. GET accepts only unique `origin/q/translationId/sourcePath/cursor/limit` keys; `q` is literal source-path text and `sourcePath` is exact. Pages default to 25 aliases, at most 50. UTF-8-safe cursors bind filters, language and registry version. SQL mutations repeat the live-session and expected-registry predicates; stale writes and invalidated list cursors return 412. The UI keeps unsaved edits and requires explicit comparison/retry after a conflict.

`0008_redirects.sql` adds route origin and per-language registries, protects canonical paths, and versions route inserts/updates/deletes plus article path changes through transactional triggers. Manual creates and all alias edits/deletes append `redirect.create/update/delete` audit records with language as subject ID and the new registry version. Automatic aliases created by content moves retain their existing page-event audit coverage. The migration replaces only the audit insert validator, preserving immutable historical rows, and remains compatible with content route inserts that omit the new origin column. No Cloudflare resource, permission or CSP expansion is needed.

Once redirect events exist, application rollback must retain the redirect-aware audit decoder; the older decoder rejects that category and cannot serve mixed audit pages. Retain all applied migrations and audit rows, and make schema repairs through forward migrations. Before the new Worker is deployed, compatible older content writes can advance registry versions without creating manual redirect events.

`migrations/0007_audit.sql` adds immutable `audit_records` with an increasing sequence. Existing page events are copied with original timestamps and `origin=legacy`, without inventing actor provenance. Future page-event inserts, navigation version updates and successful administrator initialization/credential changes append records through database triggers in the same transaction. Audit failure rolls back the originating operation. Earlier navigation/account history, login/logout and failed attempts are not synthesized. `origin=current` means captured after the migration, not an independently verified actor attribution.

Audit details use closed category-specific schemas enforced in SQL and decoded again in `worker/audit/service.ts`: page revision/from/to references; navigation previous/current mode and node count; redirect before/after source paths and target IDs; credential-change booleans, or null for initialization. No Markdown, change notes, navigation labels/URLs, usernames, credential hashes, bearer values, IPs or request payloads enter these records. An owned revision join supplies an optional historical page title. `AuditService(db, ContentWriteAccess).list()` applies the live-session SQL predicate and returns at most 50 records (default 25), ordered by sequence descending. Its canonical base64url cursor binds category/action/language/subject/time filters; it does not contain credentials. UTC millisecond bounds are inclusive from and exclusive to. `/api/admin/audit` accepts only GET with exact, non-repeated query keys; there are no audit mutation or deletion endpoints. Other administrator response and CSP policies remain unchanged.

Future modules: file lifecycle, site settings and deliberate caching. Keep storage in Worker-side repositories with portable domain contracts. Do not expose a new privileged operation without both HTTP access checks and the service's SQL session/version guards.

D1 stores articles, translations, revisions, route aliases, audit events, publication search, navigation, the audit trail and authentication state; settings will also use D1. R2 is planned for files with D1 metadata. KV is optional for explicitly eventually consistent cases, not the authoritative database by default. Cache API may serve published content with language/version keys and deliberate invalidation. Queues, Workflows, Durable Objects, Images, Access, Workers AI, Vectorize, Browser Rendering and Containers are allowed only with concrete need. Provision none speculatively. Remote migrations must be reviewed/repeatable and run in Actions, with recovery planning before destructive changes.

Forbidden infrastructure: VPS, persistent production Node servers, always-on Docker servers, external PostgreSQL/MySQL/Redis and traditional independently maintained backend servers.

## Environments and permissions

Current test Custom Domain: `https://cf.emby.wiki`, Worker `cloudflare-wiki`. The stable `cloudflare-wiki.<account-subdomain>.workers.dev` address is enabled only for GitHub Actions automated smoke testing; the deployment script reads the account subdomain through Cloudflare's API rather than hardcoding it. Preview URLs remain disabled. Future production: `https://emby.wiki`; no current workflow/config may deploy it. No production environment, route, wildcard route or migration command exists.

Local Codex uses Cloudflare read-only credentials for authorized inspection of Workers/D1/R2/KV, routes/domains, configurations/state and readable logs. Never deploy, create/delete/modify resources, migrate remotely, change DNS/routes, upload R2 or write KV locally. Do not use write-capable OAuth locally. Actual token permissions enforce this boundary; scripts and written rules add guardrails but cannot replace IAM.

All writes use `secrets.CLOUDFLARE_API_TOKEN` in Actions only. Never retrieve its value or place it in local files, docs, browser variables, artifacts or logs. Actions Variables: actual `CLOUDFLARE_ACCOUNT_ID`, actual `CLOUDFLARE_ZONE_ID`, `CLOUDFLARE_WORKER_NAME=cloudflare-wiki`, `TEST_DOMAIN=cf.emby.wiki`. Missing values are reported by name, never fabricated.

Optional `secrets.ADMIN_SETUP_TOKEN` belongs only to the Actions deployment step. The owner supplies a canonical unpadded base64url token representing at least 32 random bytes (43–256 characters) and keeps it outside the repository. `scripts/admin-bootstrap.mjs` validates the same exact-source Actions guards as deployment, hashes the token with SHA-256, and sends only its hash to owned D1 after migrations and before deployment. The caller deletes the raw environment value before starting Wrangler; it is never a Worker binding or CLI argument. Without the secret, bootstrap is skipped and public deployment continues. Removing the secret does not revoke an existing unconsumed window.

The bootstrap statement grants a 24-hour window only when no administrator exists and the bootstrap is unconsumed. A repeated deployment with the same hash never extends or reopens the window, including after expiry. Before initialization, an explicitly changed Actions secret can rotate the hash and start a new window. An existing administrator or consumed marker prevents all reopening. Unknown write outcomes stop without automatic retry; output includes status only, never a token/hash. Do not clear the consumed marker or delete the administrator as a recovery shortcut. Local development does not receive this token; auth tests use isolated fixtures.

Preflight verifies zone/account, existing Worker ownership and domain associations and rejects conflicting DNS/routes. The ownership marker is a consistency check, not authentication. Wrangler creates/updates the fixed Worker and test Custom Domain; repeated runs reuse them. Actions owns the fixed D1 database `cloudflare-wiki-test` and DB binding. `0001_project.sql` establishes the ownership marker, `0002_content.sql` establishes the content schema and `0003_starter_content.sql` publishes the original seed. The source UUID is a local-only placeholder. The deployment script resolves the actual UUID, requires matching ownership and a known migration-ledger prefix on existing databases, applies pending migrations once, and verifies the full ledger plus deployed Worker binding. Both Wrangler automatic provisioning flags are disabled. An unmarked existing database stops the workflow; a failed first initialization needs explicit recovery authorization, never implicit adoption or deletion. No R2/KV exists yet. Stop for payment, permission expansion, resource deletion, production changes or weaker security. Incompatible existing resources need an owner decision, not silent replacement.

## Git, CI and deployment

Sync main, create an allowed task branch, develop, validate, commit, push, PR, passing CI, resolved conversations, authorized squash merge. Never develop/push directly to main, force push or rewrite history. Apply the supplied main Ruleset after CI exists: PR required, current `CI` required, resolved conversations, no deletion/force push, linear history and squash only. No bypass actors. Zero mandatory external approvals accommodates one maintainer; PR/CI remain mandatory.

`CI` runs on PRs and main pushes: locked dependency install, lint, format check, generated Worker types, separate frontend/Worker/tooling typechecks, tests, build and smoke against built output in workerd. It has no deployment credential.

`Deploy Test` runs on main pushes and manual main dispatch only. It validates the exact commit again, preflights settings/resources, provisions or validates owned D1 and applies reviewed migrations, optionally provisions the guarded bootstrap hash, deploys, confirms the `cf.emby.wiki` Custom Domain binding through Cloudflare API readback, and smoke-checks the stable Workers.dev address for server-rendered articles, search, metadata, sitemap, genuine 404s, JS asset, health JSON, exact revision and robots policy. Anonymous GET smoke checks also verify the admin shell, session/overview/content/navigation/redirect/audit 401 responses and setup-status booleans; they never initialize an administrator or create a session. Main deployment concurrency prevents overlapping writes. PRs never deploy. Only the deploy step receives the secrets. Read failed run/job/step/log evidence and fix through PRs; do not disable gates. A passing build alone does not complete initialization.

## Security and Codex configuration

Static responses use CSP, frame denial, no-sniff, referrer policy and noindex. APIs use no-store and reveal no credentials. Future uploads require MIME/size limits, safe filenames, normalized paths, authorization and public/private separation; public downloads need safe content disposition. Prevent unbounded rendering work, SSRF in imports, open redirects, unsafe HTML and cache leaks. Validate inputs and authorize writes server-side. Pin dependencies/Actions, review upgrades and scan staged content.

`.codex/config.toml` contains officially documented project settings: on-request approvals and workspace-write sandbox. It does not start a goal, force a model or grant cloud permissions. Trusted-project loading and local configuration precedence apply.

## Database recovery

Migrations are additive and applied remotely only by the main Actions workflow. Existing revisions and audit events are retained, including after soft deletion. Do not edit or remove applied migration files, reset the ledger, drop tables or delete the database to fix a deployment. Application rollbacks use normal PRs that retain the DB binding and migration history; schema repairs use forward migrations. If an initial database exists without a committed project marker, stop for an explicit recovery decision.
